# Copilot Instructions for .NET C# and Flutter Development

## Core Development Principles

### Think Like a Programmer
- **Analyze before acting**: Always understand the current state before making changes
- **Root cause analysis**: Don't treat symptoms, fix the underlying issues
- **Incremental changes**: Make small, testable changes one at a time
- **Verify assumptions**: Test configurations and connections before proceeding
- **Clean slate approach**: Start with known-good states when debugging

### Environment Management
- **Always start clean**: Remove conflicting containers, ports, and processes before starting
- **Check for conflicts**: Verify ports, container names, and resources are available
- **Isolate environments**: Demo, Development, and Production should be completely separate
- **Document state**: Know what's running, what ports are used, and what databases exist
- **Clean shutdown**: Always properly stop services before making changes

## .NET C# Best Practices

### Service Configuration
- **Environment-specific appsettings**: Use `appsettings.{Environment}.json` for configuration overrides
- **Port consistency**: If a service runs on port 8081 internally, map it correctly externally
- **Connection strings**: Use environment variables for database connections in Docker
- **Health checks**: Implement proper health endpoints for service monitoring
- **Logging**: Use structured logging to debug connection and startup issues

### Port Management Strategy ⭐ CRITICAL
Our dating app uses a systematic port strategy to avoid conflicts:

**Development Environment (Local):**
- Auth Service: 8081 (internal) → 8081 (external)
- User Service: 8082 (internal) → 8082 (external)  
- Matchmaking Service: 8083 (internal) → 8083 (external)
- Database: 3306 (internal) → 3306 (external)

**Demo Environment (Docker):**
- Auth Service: 80 (internal) → 5001 (external)
- User Service: 80 (internal) → 5002 (external)
- Matchmaking Service: 80 (internal) → 5003 (external)
- Database: 3306 (internal) → 3307 (external)
- YARP Gateway: 80 (internal) → 5000 (external)

**Why This Matters:**
- Internal ports MUST match what the service listens on inside the container
- External ports are what clients/other services use to connect
- Environment variables (ASPNETCORE_URLS) should match internal container port
- appsettings.{Environment}.json should override default ports when needed

### Configuration Priority (Highest to Lowest)
1. **Environment Variables** (docker-compose environment section)
2. **appsettings.{Environment}.json** (e.g., appsettings.Demo.json)
3. **appsettings.json** (default fallback)
4. **Hardcoded values** (avoid these!)

### Connection String Best Practices
```csharp
// ❌ BAD: Hardcoded in appsettings.json
"Server=localhost;Port=8081;Database=mydb"

// ✅ GOOD: Environment variable override in docker-compose
"ConnectionStrings__DefaultConnection=Server=mysql-demo;Database=auth_service_demo;Uid=root;Pwd=demo_root_password;"

// ✅ GOOD: Docker service names instead of localhost
"Server=mysql-demo" // Not "Server=localhost"
```

### Docker and Containerization
- **Build context**: Ensure Dockerfile COPY paths match the actual project structure
- **Service naming**: Use lowercase service names in docker-compose to avoid image naming issues
- **Port mapping**: Map external ports to the actual internal ports services listen on
- **Dependency order**: Use proper `depends_on` to ensure services start in correct order
- **Volume management**: Clean up volumes when making schema or data changes

### Docker Build Configuration ⭐ LESSONS LEARNED
**Problem:** appsettings.Demo.json files weren't being copied to Docker containers

**Solution:** Update .csproj files to explicitly include environment-specific configs:
```xml
<ItemGroup>
  <None Include="appsettings.Demo.json">
    <CopyToOutputDirectory>Always</CopyToOutputDirectory>
  </None>
</ItemGroup>
```

**Why This Happened:**
- .NET publish only includes files marked for output by default
- Some projects had `<CopyToOutputDirectory>Never</CopyToOutputDirectory>` for all appsettings
- Environment-specific files need explicit inclusion
- Multi-stage Docker builds only copy the published output, not source files

**Prevention:**
- Always verify environment files exist in containers: `docker exec CONTAINER ls /app/appsettings*`
- Test environment-specific configurations locally before Docker builds
- Use consistent .csproj configuration across all services

## Development Workflow

### Before Making Changes
1. **Stop all running services** to avoid conflicts
2. **Check port availability** with `lsof -i :PORT` or `netstat`
3. **Clean Docker state** with `docker system prune` if needed
4. **Verify file paths** are correct for the current working directory
5. **Check git status** to understand current state

### When Debugging Issues
1. **Read error messages completely** - don't assume the problem
2. **Check service logs** with `docker logs CONTAINER_NAME`
3. **Verify connectivity** with basic tools like `curl` or `telnet`
4. **Test database connections** independently
5. **Isolate the problem** by testing components individually

### Configuration Management
1. **Use environment variables** for different deployment targets
2. **Validate configurations** before starting services
3. **Document port assignments** and service dependencies
4. **Keep working configurations** in version control
5. **Test configuration changes** in isolation

### Iteration Best Practices
1. **Make one change at a time** and test it
2. **Keep working states** - don't break what's already working
3. **Use feature branches** for experimental changes
4. **Document what works** for future reference
5. **Automate repetitive tasks** with scripts and tools

## Debugging Commands and Tools

### Docker Management
```bash
# Clean start
docker-compose down && docker system prune -f
docker-compose up -d

# Check service status
docker-compose ps
docker logs SERVICE_NAME --tail 20

# Port inspection
docker port CONTAINER_NAME
lsof -i :PORT_NUMBER
```

### Configuration Troubleshooting ⭐ STEP-BY-STEP
When services aren't responding correctly:

1. **Check What Port Service Is Actually Listening On:**
```bash
docker logs CONTAINER_NAME | grep -i "listening\|started\|port"
# Look for: "Now listening on: http://[::]:PORT"
```

2. **Verify Environment Files Exist in Container:**
```bash
docker exec CONTAINER_NAME ls -la /app/appsettings*
# Should show appsettings.Demo.json if ASPNETCORE_ENVIRONMENT=Demo
```

3. **Test Internal vs External Connectivity:**
```bash
# Test external port (what clients use)
curl http://localhost:EXTERNAL_PORT/health

# Test internal port (what docker-compose maps to)
docker exec CONTAINER_NAME curl http://localhost:INTERNAL_PORT/health
```

4. **Check Docker Port Mappings:**
```bash
docker port CONTAINER_NAME
# Should show: INTERNAL_PORT/tcp -> 0.0.0.0:EXTERNAL_PORT
```

5. **Verify Database Connectivity:**
```bash
# Check if service can reach database
docker exec SERVICE_CONTAINER ping mysql-demo
# Check database is accepting connections
docker exec mysql-demo mysql -u root -p -e "SHOW DATABASES;"
```

### Port Debugging Workflow
```bash
# 1. Check what ports are in use
netstat -tlnp | grep :PORT_NUMBER

# 2. Check docker-compose port mapping
grep -A 5 -B 5 "ports:" docker-compose.yml

# 3. Check service's actual listening port  
docker logs SERVICE_NAME | grep -i "listening"

# 4. Test the mapping
curl -v http://localhost:EXTERNAL_PORT/health
```

### .NET Service Debugging
```bash
# Check service endpoints
curl -v http://localhost:PORT/health
docker exec CONTAINER curl http://localhost:INTERNAL_PORT/

# Database connectivity
docker exec DATABASE_CONTAINER mysql -u USER -p
```

### Flutter Development

```bash
flutter clean && flutter pub get
flutter run -d DEVICE_ID

# Debug connection issues
flutter logs
```

## Common Pitfalls to Avoid

### Configuration Issues
- ❌ Changing working configurations without understanding why they worked
- ❌ Ignoring port conflicts and trying to work around them
- ❌ Using hardcoded values instead of environment-specific configurations
- ❌ Not cleaning up old containers and volumes before starting fresh

### Port and Environment Mistakes ⭐ REAL EXAMPLES FROM TODAY
**What Went Wrong:**
1. **Inconsistent Port Mapping**: Docker-compose mapped `5001:8081` but service listened on port 80
2. **Missing Environment Files**: appsettings.Demo.json existed but wasn't copied to containers
3. **Configuration Priority Confusion**: Environment variables vs appsettings vs hardcoded values
4. **Database Connection Mismatch**: Used `localhost` instead of Docker service names

**How to Avoid:**
- Always check what port a service actually listens on: `docker logs SERVICE_NAME | grep "listening"`
- Verify environment files in containers: `docker exec CONTAINER ls /app/appsettings*`
- Use `curl` to test actual endpoints after changes: `curl http://localhost:EXTERNAL_PORT/health`
- Check docker-compose environment variables match service expectations
- Use Docker service names for internal communication, not localhost

**Red Flags to Watch For:**
- Services showing "Connection refused" or "Connection aborted"
- Warning messages about "Overriding address" in logs
- Services that work in development but fail in Docker
- Database connection failures after container restarts

### Development Process
- ❌ Making multiple changes simultaneously without testing
- ❌ Assuming services are working without proper health checks
- ❌ Not checking current working directory when dealing with relative paths
- ❌ Treating symptoms instead of identifying root causes

### Service Integration
- ❌ Starting dependent services before their dependencies are ready
- ❌ Not verifying database schemas and permissions
- ❌ Ignoring connection errors and hoping they resolve themselves
- ❌ Using inconsistent service names between different configuration files

```yaml

      - dating-demo-network
```
